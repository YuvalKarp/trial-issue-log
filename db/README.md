# Database

PostgreSQL 16. The schema lives in `migrations/` as plain SQL files, applied in filename order by the server on startup (`server/src/db/migrate.js`). Applied files are recorded in the `schema_migrations` table, so each one runs once.

## Table: `issues`

| Column | Type | Notes |
|---|---|---|
| `id` | integer, identity | Primary key, generated by the database |
| `title` | text | Required, 1-200 characters |
| `description` | text | Required |
| `site` | text | Required, e.g. `Site-101` |
| `severity` | text | `minor`, `major` or `critical` (CHECK constraint) |
| `status` | text | `open`, `in_progress` or `resolved` (CHECK constraint), defaults to `open` |
| `created_at` | timestamptz | Defaults to `now()` |
| `updated_at` | timestamptz | Set by a `BEFORE UPDATE` trigger |

## Design choices

- **CHECK constraints instead of ENUM types.** Adding a new severity or status later is a one-line migration, with no type to alter.
- **`updated_at` is set by a trigger, not by the application.** Every update path gets it right, including a manual fix in SQL.
- **Constraints are duplicated in the database on purpose.** The API validates input first (and returns a 400), but the database is the last line of defence against bad data.
- **Index on `(created_at DESC, id DESC)`.** Matches the only sort order the list uses.
- **`timestamptz`.** Timestamps are stored as absolute points in time and returned as ISO 8601 in UTC.

## Adding a migration

Create the next numbered file, e.g. `002_add_assignee.sql`. Never edit a migration that has already been applied; add a new one instead.
